## 一、必须修复（P0 / P1）

### ①【P0】韵脚数据路径未走 `locate()`，非仓库根目录运行会崩溃
- 位置：`src/shijing/cli.py`
  - `build_parser()` 中 `--rhyme-data` 默认值为 `str(ancient.DEFAULT_PATH)`，即相对路径 `data/rhyme_baxter1992.csv`（约第 332 行）。
  - `cmd_rhyme_ancient()` 直接 `path = args.rhyme_data` 后传给 `ancient.schemes / summary / compare_modern`（约第 141 行），**没有经过 `locate()`**。
- 对比：`CORPUS` / `RAW` / `OVERRIDES` 在 `load_corpus()` 里都走了 `locate()`，可"在任意工作目录运行"。`rhyme-data` 漏掉了，破坏了一致性。
- 实证：在临时子目录里 `ancient.load('data/rhyme_baxter1992.csv')` 直接 `SystemExit: 找不到韵脚数据 data\rhyme_baxter1992.csv`。
- 影响命令：`shijing rhyme --system ancient`（及其 `--what summary|compare|table`）在仓库根以外运行必崩。
- 修复建议（二选一）：
  ```python
  # 方案 A：命令里解析（推荐，与其它数据路径一致）
  def cmd_rhyme_ancient(args, c):
      path = locate(args.rhyme_data)        # 加这一行
      ...
  ```
  ```python
  # 方案 B：ancient.load 内部容错回退
  def load(path=DEFAULT_PATH):
      p = Path(path)
      if not p.is_absolute() and not p.exists():
          cand = Path(__file__).resolve().parents[2] / 'data' / 'rhyme_baxter1992.csv'
          if cand.exists():
              p = cand
      if not p.exists():
          raise SystemExit(...)
  ```

### ②【P1】`search` 无命中时 JSON/CSV 输出人类文本，脚本消费者会解析失败
- 位置：`src/shijing/cli.py` `cmd_search()`（约第 197–199 行）
  ```python
  if not rows:
      print('没有命中。')     # 三种 --format 都走这里
      return 0
  ```
- 问题：`--format json` 时 stdout 是纯文本 `没有命中。`，下游 `json.loads` 直接抛异常；`--format csv` 同理只落一句提示。
- 对比：`name` 命令即使无命中也输出**合法 JSON**（`emit(data, 'json')`），两者行为不一致。
- 注意：现有 `test_检索无命中不报错` 把该行为写死为断言（`'没有命中' in out` 对三种 format 都成立），改动时**需同步改测试**。
- 修复建议：
  ```python
  if not rows:
      if args.format == 'json':
          print(json.dumps([], ensure_ascii=False))
      elif args.format == 'csv':
          print('group,title,stanza,line')   # 仅表头，或加注释行
      else:
          print('没有命中。')
      return 0
  ```

### ③【P1】`__init__.__version__` 与 `pyproject.toml` 版本脱节
- 位置：`src/shijing/__init__.py` 第 7 行 `__version__ = '0.2.0'` vs `pyproject.toml` 第 7 行 `version = "0.4.0"`。
- 目前没有 `--version` 命令所以不暴露，但一旦加命令或被其它工具 `import` 读取，会给出错误版本号。建议单一来源：
  ```python
  from importlib.metadata import version as _v
  __version__ = _v('shijing')
  ```
  或构建期注入。

## 二、性能 / 设计优化点（P2）

### ④【P2】`ancient` 多次重复读取整张 CSV
- 位置：`src/shijing/ancient.py`
  - `summary()` 内部依次调用 `schemes()`（→`load`）、`rhyme_classes()`（→`load`）、`co_rhymes()`（→`rhyme_classes`→再 `load`）。
- 实证：单次 `summary(c)` **打开 `rhyme_baxter1992.csv` 3 次**（7286 行 / 251KB）。
- `cmd_report` 还会再触发 `ancient.summary` + `ancient.compare_modern`，单次 report 读盘 4–5 次。
- 修复建议：
  ```python
  from functools import lru_cache
  @lru_cache(maxsize=1)
  def load(path: str | Path = DEFAULT_PATH) -> dict[int, list[Clause]]: ...
  ```
  或让 `schemes/summary/compare_modern` 复用同一个 `data` 对象（参数传递而非反复 `load`）。CSV 是静态资源，`lru_cache` 最省事。

### ⑤【P2】`naming` 每次全量重算字频 + 逐字全语料线性扫描
- 位置：`src/shijing/naming.py`
  - `char_facts()` 每次都 `analyze.char_stats(corpus)`（全语料重算，约第 95 行）。
  - `char_sources()` 对每个不同字调用 `hits(corpus, ch)`，`hits` 再把全部 poem×stanza 扫一遍、且每次 `normalize(st)` 重跑（约第 122 行）。
- 现状：`name` 命令是 O(N²) 量级的重复扫描，305 篇 / 3 万字下是毫秒级，不影响使用；但属于明显可消除的重复劳动。
- 修复建议：在 `naming` 里构建一次 `字 -> [(poem_idx, stanza, line)]` 倒排索引（`corpus` 加载后算一次），`char_facts` / `char_sources` / `hits` 共用；`char_stats` 结果在 `cmd_name` 内缓存一次。

### ⑥【P2】数据目录定位硬编码 `parents[2]`
- 位置：`src/shijing/clean.py` 第 20 行 `_table()` 用 `Path(__file__).resolve().parents[2]`；`src/shijing/cli.py` 第 25 行 `locate()` 用 `here.parents[2:4]`。
- 两处都假设"包位于 repo 下恰好两层"。将来拆子包/改目录结构会静默失效（读不到 `data/`）。
- 修复建议：抽一个共享常量，例如
  ```python
  REPO_ROOT = Path(__file__).resolve().parents[2]   # 仅在一处定义
  DATA_DIR  = REPO_ROOT / 'data'
  ```
  或改用 `importlib.resources` 读取随包数据。CLI 的 `locate()` 也应统一引用它，而非自己再算一次 `parents[2:4]`。

### ⑦【P2】`visuals.find_font` 显式字体参数重复检查
- 位置：`src/shijing/visuals.py` 第 26–30 行
  ```python
  for cand in ([explicit] if explicit else []) + FONT_CANDIDATES:
      if cand and Path(cand).exists():
          return cand
  if explicit and Path(explicit).exists():   # 上面已经覆盖，这句是死代码
      return explicit
  ```
- 修复：删掉重复的 `if explicit ...` 分支；若用户 `--font` 指定路径但不存在，应在探测前**尽早**给出清晰报错，而不是落到末尾的通用 `SystemExit`。

### ⑧【P3】`rhyme.label_scheme` 韵部 > 26 时字母碰撞
- 位置：`src/shijing/rhyme.py` 第 66 行 `letters[f] = chr(ord('A') + len(letters) % 26)`。
- 单篇内不同韵部一般不会超过 26，但属隐患；可改用 `string.ascii_uppercase` 循环或多字母（AA/AB…）。低危，仅影响显示。

### ⑨【P3】`refrain.summary` 重复调用 `reduplications(corpus)`
- 位置：`src/shijing/refrain.py` 第 111–112 行，`reduplications(corpus)` 被调了两次（取 total 与 kinds）。一次取出复用即可。微优化。

## 三、算法 / 正确性边界风险（需知晓，非必改）

### ⑩【关注】`drop_stitched_stanzas` 依赖"本篇无平行章才判外来"，存在漏判可能
- 位置：`src/shijing/corpus.py` 第 243–301 行。
- 核心规则：尾部段若与本篇其余章**平行**则判为正本保留。这意味着：
  - 外来整章**恰好与本篇其余章平行（巧合）** → 会被误留（漏判串台）；
  - `len(p.stanzas) < 3` 的篇目直接跳过检测 → 短篇若被串台会漏检。
- 当前 305 篇回归测试全部通过（`test_跨篇粘贴串台已剔除` / `test_语料内不再有整章跨篇重复`），说明**现有语料未触发**上述边界。
- 建议：
  1. 增加回归断言：构造"一条 ≥12 字的长套语跨篇复现且位于某篇尾部"的情形，确认不被误删；
  2. 在模块 docstring / README 明确"此法对巧合平行的串台可能漏判"；
  3. 长远可把判定升级为"尾部整段与另一篇的连续章逐字相同且构成完整该篇块"，而不仅是"与本篇平行度"。

### ⑪【关注】`off_position_rhymes` 依赖 `clause` 字段是纯汉字的隐式契约
- 位置：`src/shijing/ancient.py` `summary()` 第 188–190 行，用 `c.positions[0] != len(c.text)` 判断韵脚是否不在句末。
- 这要求 `clause` 不含标点（data/README 已保证"只留汉字"）。若将来 raw 混入标点，位置比较会失准。
- 建议：在 `load()` 里对 `clause` 统一做一次 `han_only` 归一并 `assert` 无残留，把隐式契约显式化。

## 四、文档 / 一致性小问题

### ⑫ 文档数字不一致
- `src/shijing/ancient.py` 模块 docstring 写"311 句是句中韵"，但 `README.md`（第 40 行）与 `CHANGELOG.md`（0.3.0）都写"317 句"；`summary()` 的 `internal_rhyme_lines` 实际由数据算得。

### ⑬ README 示例略误导
- `README.md` 第 135 行推荐 `chars --top 200`，但 `chars` 默认 `--top 30`，需显式传参。示例可补 `--top 200`。

### ⑭ `name` 命令 `--top` 语义未写明
- `--top` 只控制"命中句"展示条数；单字出处示例固定 3 条（`char_sources(limit=3)` 写死），与 `--top` 无关。属预期行为，但文档可点明，免得开发/用户误以为 `--top` 控制示例数。

## 附：总体评价

优点（值得保留）：
- **数据清洗思路扎实**：以"正文指纹去重 + 跨粘贴多数表决 + 覆盖表"还原 305 篇，且有自证式回归（篇数、字数、串台剔除全部断言），不易回退。
- **`name` 命令定位克制且正确**："只给可核验材料、不判吉凶"的边界声明（README 诚实边界一节）比多数同类项目成熟，避免把使用者偏好伪装成统计。
- **上古音口径替换今音口径 + 与 Baxter 表逐字校验**是本轮最大的价值点，直接消掉了"今音猜韵"的方法性错误。
- 工程基础到位：类型注解、`dataclass`、模块化、`ruff`（E/F/I/UP/B）选型合理、CI 覆盖 3.10–3.12。

主要短板（按优先级）：
- **P0**：`rhyme-data` 路径未 `locate`，子目录崩溃。
- **P1**：`search` 无命中 JSON/CSV 输出非结构化文本；`__version__` 与 pyproject 脱节。
- **P2**：`ancient` 多次重复读盘、`naming` 重复扫描、`data` 目录定位硬编码两层。

合并建议：先把 ① ③ ② 清掉（都是小改动、低风险），④ ⑤ ⑥ 可排进下一轮"性能/健壮性"批次。

### 剩余可优化（非必须，留作下一轮）

1. **`ancient.schemes` 仍带取模**：`ancient.py` 第 134 行用 `_ALPHA[len(letters) % len(_ALPHA)]`（52 标签取模）。单篇内不同 (章, 标签) 组数不可能超 52，实际不会撞，但和 `rhyme.label_scheme` 已"去取模"的做法不一致。建议同样改成 `[len(letters)]` 取下标，彻底消除隐患，与 ⑧ 的修法对齐。
2. **全量 `pytest` 未在本机跑**：受网络限制（PyPI 经代理下载被 `IncompleteRead` 截断），`jieba/pypinyin` 装不上，无法本地执行 77 项。上述结论已用解释器走真实代码路径覆盖核心分支；若 CI 在 GitHub Actions 上跑通（开发团队称 77 项全绿），即可采信。建议本地确认一次 `pytest -q` 收尾。
3. **`report` / `compare_modern` 仍依赖 `pypinyin`**：属既有设计（今音对照口径），非回归；只是说明出 `report` 需要该依赖，CI 的 `.[dev]` 已含。
